## Improvements

1. Resolve worker policy on the host that launches the worker. `spawn/index.ts` builds `plan.workers` on the originating orchd. `handlers/lifecycle.ts` forwards it unchanged and uses `params.workers` in `BackendSpawnOpts`, even though the receiving orchd already reads its own `settingsFor(params.project)`. Reuse the local policy resolver on the receiving orchd with the remote project over the remote install, preserving the explicit read-only request. Derive the worker tools and policy env from that same result. Test with conflicting origin and destination settings and an omitted project key that must inherit from the destination. This needs a harness-neutral core change, not a Claude branch.
2. Keep argv construction free of writes. For the second Open question: no, a deterministic path does not make file I/O a build step. `spawn/models.ts` builds previews without `orchDir`; `handlers/relaunch.ts` also uses those builders to produce a real restart command, so the proposed branch silently omits `--settings` there. Name the actual launch, resume and restart entry points, pass the effective project policy on each, and put any necessary preparation behind a harness-neutral launch hook. Don't rely on `refreshStaleShims` as a guarantee: admission refreshes on the requesting host, the receiving headless handler does not, and `restartHere` only refreshes for an explicit harness in its plain restart path. The refresh itself can warn and continue. Test preview purity and the real restart command separately.
3. Settle the native settings transport before committing to files. The repo proves the current file mapping and the unquoted `join(" ")`, not Claude's inline `enabledPlugins` support, `env` precedence, or when a running session rereads its settings. Verify those against the supported Claude version. If inline JSON can carry the policy, use the existing shell quoting helper at the shell boundary and leave raw argv unquoted for Herdr and headless launches. Don't put arbitrary user settings or secrets on the process command line. If a file is necessary, spell out why it is native launch configuration under Rule 18. orch must take policy from the launch request, never infer policy or liveness from a generated file.
4. If files remain, make them immutable snapshots keyed by the complete rendered settings, including inherited user keys and hooks. A policy-only digest lets the next launch replace a file an earlier process has not opened yet when the base changes. Use the full digest rather than a hardcoded 16-character cutoff, derive paths from the existing adapter config path or declare the new path as configuration under Rule 17, and publish with unique same-directory temp files and atomic rename. Share the writer with install sync, which currently writes in place. Parse JSON as `unknown` with `isRecord`, reuse one malformed-file diagnostic, and distinguish a missing file from an unreadable one instead of treating every read error as empty. For the first Open question: don't prune in doctor. Live store rows do not cover the window between snapshot publication and process start; defer retention rather than guessing from the filesystem.
5. Narrow the claim to the two affected policy values or specify how Claude will honor the rest. `claude.ts` does not map every `WorkerPolicy` field: for example it never reads `inheritExtensions` or `allowTools`, and `readOnlyPolicy` sets `inheritExtensions: false`. Correct the test plan too: the effort fixture near line 189 has no `workers` and should keep expecting `claudeSettingsPath`; add an explicit policy fixture and assert `enabledPlugins` is a map of plugin IDs to `false`. Add concurrent launches with different policies and with the same policy across a base settings change, and cover read-only connector suppression and paths with spaces. Cite repository history or remove the unverified claim that running sessions took the last project's settings after a rewrite.
