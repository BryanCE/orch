## Improvements

1. Stop forwarding origin-generated policy env. Part A overlays the destination's `policyEnv` on `params.env`, but `spawn/index.ts` filled that env with the origin's `policyEnv`, and `spawnOnHost` forwards it. If only the origin sets a compaction point, the destination emits no key and the origin's value survives. Send only non-policy env across the link and derive policy env and tools at the destination. The wire can stay the same, but `workers` is optional in the current schema, so specify `params.workers?.readOnly ?? null` on receipt. Test a destination with no compaction point as well as one with a different point. I agree with Sonnet that policy must be consistent across a linked spawn and restart; resolving on the destination is better than declaring the origin authoritative.
2. Specify which restart path actually runs the prepared launch and what policy it can replace. `planRelaunch` produces only a shell command. The held relaunch role reuses the old environment, and the pane fallback submits the command into the old shell. Passing `orchDir` fixes the two file-backed keys, but does not refresh env-backed policy. Also, the pane fallback calls `recordedHarness(..., "restart")` before planning, and Claude declares no native restart text. Don't imply it becomes a supported restart merely because a command can be rendered. Specify the supported paths, refresh once for the adapter that actually launches after branch selection, and validate/build before ending the old process. Test an actual held restart with changed project settings, not just `planRelaunch` output. I agree with both reviews that passing `orchDir` is necessary; it is not enough to prove restart behavior.
3. Give install setup, sync, diagnosis and launch one explicit read contract. `readInstallSettings` cannot throw on absence by wrapping today's `readWorkerSettings`, which returns `{}` for every read error. If `expectedWorkerSettings` unconditionally uses the new strict reader, setup cannot create the first file. Parse once from `unknown` with `isRecord`, distinguish `ENOENT` using `errnoCode`, and let setup and diagnosis treat only absence as empty. Make launch refuse unreadable, malformed or missing config. `isRecord(install.hooks)` also accepts `{}` and stale hooks; since `refreshStaleShims` can warn and continue, define what launch verifies and test empty hooks and fresh setup. I agree with Opus and Sonnet on one atomic writer and no pruning; the content digest now addresses their base-change race. Check the same-pid temp-name assumption against setup and sync writers, and clean up a failed temp write.
4. Finish the resolver and preview wiring. Give `planSpawn` and `relaunchPolicy` an explicit source for `OfferedModels`, name the direct test callers that need new arguments, and say how the shared resolver keeps the able-harness refusal without importing adapter implementations into `policy/workers.ts`. Mark the `tileAgent` command passed to `prepareWorkspace` as a preview too. Specify the conversion from the required nullable command input to the optional `SpawnOpts.orchDir` field. Keep shim/argv side effects out of previews; I accept the builder write under that contract for the audited call sites, not as a guarantee inferred from a path alone.
5. Fix quoting at Claude's shell boundary instead of deferring it for every adapter. The new file argument still cannot reach a Claude worker intact when `orchDir` contains whitespace. Use the shell formatter appropriate to the supported shell, and leave Herdr, resume and headless raw argv untouched. Add a test with a spaced directory. I agree with retaining native settings files rather than putting user keys on argv, but not with treating an existing launch failure as compatible with the plan's every-launch guarantee. For Rule 17, derive the snapshot directory from the existing config convention or declare the new path in settings; naming a literal as a constant does not by itself make it configurable.
