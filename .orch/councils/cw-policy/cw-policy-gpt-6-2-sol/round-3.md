## Improvements

1. Move preparation for a new tab ahead of pane creation, and carry its result through launch. `spawn/index.ts` already builds policy env in `prepareAgents`, passes it to `groupHome.create` and `placement.open`, then hands it to `spawnOneIntoTab` as `spec.env`. `placement.ts` uses that env in preference to computing one. Calling `prepareLaunch` only in `spawnOneIntoTab` is too late for a pre-opened pane, and deleting `plan.workers` leaves the earlier env builder with no input. Prepare once before opening the pane and reuse that launch policy for opts, env and read-only registration. For tile and existing-tab growth, prepare before their placement opens. Specify how `DaemonState` reaches these sites: `spawnOneIntoTab` currently takes `DaemonContext`, which lacks `settingsFor` and `models`. Test the env at group creation and later pane placement, not only in the adapter opts.
2. Make in-place restart apply the policy it resolves, or have Bryan explicitly narrow the ruling. Part C says it keeps the last launch's env even if the current project changes or removes an env-backed setting. That contradicts the plan's every-launch guarantee. Pass an env replacement through a harness-neutral relaunch contract, or rebuild the process in a fresh environment; an overlay alone cannot remove an old key. Test a supported held restart where the project removes a compaction point. Keep the pane refusal where the recorded adapter has no restart verb. I agree with Opus and Sonnet about one refresh per launch, but not about doing it at the top of `restartHere` before the path and target are validated. Also keep the refresh in `reloadHere`: line 91 is a reload, not a launch, and Part A currently deletes it without a replacement.
3. Don't treat `EPERM` or `EBUSY` as proof that a snapshot exists. A digest describes the intended contents, not whether rename failed because an existing target is open, a directory denies the operation, or the target was never published. The same writer also writes the mutable install file, where the digest argument cannot apply at all. Propagate ambiguous publish failures after cleaning up, or use a snapshot-only publication operation that positively reports the target already exists without reading its contents. Test failure on the first publish and on an install update, in addition to repeated publication. I agree with Sonnet that Windows rename behavior needs an answer and with both reviewers on the full digest, tagged reader and no pruning; swallowing an ambiguous error is not that answer.
4. Finish the wire and preview migration. I agree with both reviews that dropping origin policy fields is better than overlaying them. Remove the unused `workerPolicy` schema, reuse the spawn read-only schema, and update every writer, reader and fixture, including `workerText` in `handlers/lifecycle.ts`, `helpers/held-far.ts`, `acp-far.test.ts`, `held-spawn.test.ts` and the wire assertions in `spawn-preferred-models.test.ts`. On linked plans, don't resolve an origin project worker policy for a preview that will not run there; `policyOf` currently still does. For tile, say that preview and launch resolve separately through the same function, or explicitly reuse one prepared result. `launchPolicy` is non-writing, not pure: `settingsFor` reads disk and `offeredModels` can query the catalogue.
5. Keep the settings transport adapter-owned, but resolve shell quoting at the common shell boundary or state the narrower supported-path guarantee. I agree with the revised ownership decision, not the claim that the known whitespace failure is compatible with every launch. Exercise shell rendering with a spaced project/install path and confirm raw argv stays unquoted. For Rule 17, precedent in `claudeSettingsPath` is not an exemption: derive the snapshot filename/layout from the existing file path without adding a hardcoded directory name, or declare the directory in settings.
