## Improvements

1. A spawn into an existing tab has no source for its `LaunchPolicy`. Row 1 of the table reads "A spawn into a new tab, or into an existing one (`prepareAgents`, `spawn/index.ts:175`)". But `spawnAgents` reaches an existing tab through `growFleetIntoGroup` at `spawn/index.ts:385-388`, and `prepareAgents` is called only from `spawnIntoNewTab` at `:313`. The existing-tab branch builds each spec inside `placeAgent` (`placement.ts:227-253`), which has `DaemonContext`, and the plan says the placement functions "resolve nothing". So no code is named that calls `prepareLaunch` for that branch, and `placeAgent` has nothing to put in `launch`. Name it: `spawnAgents` calls `prepareLaunch` once per agent before `growFleetIntoGroup`, and passes the results in as a parameter, for example `launches: ReadonlyMap<string, LaunchPolicy>` keyed by agent name. A refusal for one agent costs only that agent, like a placement failure in `growFleetIntoGroup`, or aborts the fleet before anything opens. Say which.

2. `LaunchPolicy` is defined in `daemon/server/launch-policy.ts`, but `TabSpawnSpec` is in `types/command.ts` and will carry it. `docs/rules/layers.md:7` says shared code never imports server code, and `types/` is shared. `check-layers.ts` checks value imports only, so a type import would pass, but it breaks the stated rule and is the kind of load `layers-baseline.json` exists to prevent. Define `LaunchPolicy` beside `WorkerPolicy` in `types/policy.ts`. It is a plain data type with no I/O. Keep `prepareLaunch` and `launchPolicy` in `launch-policy.ts`. `LaunchRequest` holds an `AgentAdapter`, which is also in `types/`, so it can move too.

3. Part C's relaunch env is not what a held spawn builds. The plan says the new PTY gets `spawnEnv(orchDir, key, adapter, form, model, launch)`. A held agent started through `spawnHeadless` or `startHeldAgent` gets `heldLaunchEnv(opts)`, which is `process.env`, then `agentLaunchEnv(opts, HELD_ENVIRONMENT_STAMP)` with `LAUNCH_ENV`, `ORCH_DIR` and `ORCH_PROJECT`, then `opts.env` (`backends/held/index.ts:170-178`, `policy/spawner.ts:47-63`). `spawnEnv` is the pane path: it adds `terminalClientEnv(adapter, form)` and omits `ORCH_PROJECT` and the held stamp. If `relaunchPid` takes `spawnEnv` as the whole env, the restarted agent loses `ORCH_PROJECT` and the stamp, and gains a terminal-client env that a held spawn never had. Say that the role takes the launch's identity and policy env, `{ key, orchDir, project, env: launch.env }`, and that `heldRelaunch` builds the PTY env with the same `heldLaunchEnv` a held spawn uses. Then the one function builds the env for the spawn and the restart. Also name the plumbing: `planRelaunch` returns `launch`, and `relaunchInPlace`, `relaunchTerminal` and `relaunchPlace` (`terminal-relaunch.ts:42,63`) pass it to `role.relaunch`.

4. A linked-host plan has no `cmd`, and the type does not say so. The plan says that a spawn on a linked host "builds no preview command" and that `policyOf` is not called. But `SpawnAgentPlan.cmd` is `string` (`plan.ts:24`), and `planSpawn` sets it for every agent, and `spawn/index.ts:129,181` and `placement.ts:230` read it. Make it `string | null`, null for a host spawn, and say who reads it. Say also that the early refusal of a harness that cannot run read-only moves for a host spawn. Today `agentPolicy` refuses it on the asking host at plan time. After the change the far host's `prepareLaunch` refuses it, after `spawnOnHost` has made the call. Say that this is accepted, and that the message is the same.

5. State what `launch.project` is for a restart. `planRelaunch` today reads `agentSettings(state, key)` for the model admission and tuning, and `launchPolicy` would read `settingsFor(request.project)` for the policy. They must be the same project, and the plan should not resolve it twice. Say that `relaunchTarget` resolves `settings` once, from the agent's recorded project, and that `prepareLaunch` takes the same project. For a form switch and `restartAttached`, `restartOpts` already has `projectDirectory(...)`. Name that as the value.

6. Finish the shim-refresh ordering for a tab fleet. With `prepareLaunch` in `prepareAgents`, the refresh now happens before the group opens, which is right. But for the headless branch of `executeHeadlessSpawn`, `prepareLaunch` runs inside `spawnHeadless`, per agent, after `claimSpawnNames` and `prepareWorkspace` have already made the worktree. A refusal there leaves a worktree. The existing `catch` calls `discardUnusedWorkspace` for exactly this, so say that it covers the new refusal, and add it to the core test list.
