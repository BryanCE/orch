## Improvements

1. **Trust.** Close the gap in automatic approval. If a granted agent sets `locked_commands.commands` and orchd preserves the other leaves of an unapproved checkout file, the new hash approves its `workers.verify_commands`, `council.models`, and `council.rounds` too. I agree with Opus that a granted write need not wait for the operator, but it can approve only that write, not unrelated content. Under a per-root write lock, mutate only a byte-for-byte approved base or a fresh empty file. Refuse set and clear against an existing unapproved file and tell the caller how to approve or remove it. Parse and hash the same snapshot, validate the complete candidate, atomically replace the file, then publish the approval. Specify that a crash between replacement and store commit leaves the file unapproved. Test a first-wave write against a cloned file and a clear after a direct edit.
2. **The resolver / RPCs / `orch settings` inside a repository.** Put the caller credential in the wire contract and state the authority checks for every mutation, including editor reset and save. `docs/rules/authority.md` says a raw terminal can have a registered row; absence of a row is not operator authority. Resolve via `callerKindOf` and `selfIdentityOf`, require operator for approval, and refuse missing credentials or missing placement where an agent is required. For a granted project write, derive the root from the local caller's stored placement, not the submitted cwd. Do not let a shell in a different directory or the editor's Install view turn a project grant into an install write. State explicitly whether an agent outside a repository can change an install value; I would refuse for project keys. Keep grant toggles operator-only and test direct RPC callers, not just CLI argument handling.
3. **The merge / Council readers.** Preserve `council.rounds` as the operator's ceiling. `daemon/server/council.ts:141–143` uses it as a refusal limit, so replacement lets a project raise the install cap. Use `min(project, install)` and have both `round` and `scores` use the result. For `council.models`, specify validation against current install composition, including the existing default-model and empty-allowlist semantics in `settings/read.ts:137–144`. An approved file can become invalid when the human changes `models.allowed` without changing the project hash. Cover that case and say how an invalid file affects round, scores and close; it must not strand running members.
4. **Trust / Words.** Define containment for paths that do not exist yet and for two writes racing with a path change. Reject absolute and parent-traversing `project.file`, symlink or junction components, and any alias of the install file even when the install is inside the project root. Canonicalize the approval root and verify that linked-worktree metadata actually links the current checkout to that root before using it for a write. `worktrees/repository.ts:16–26` follows `.git` and `commondir` pointers without proving the link. Require exclusive temp creation and a write strategy that cannot leave the validated directory after checking it. Add tests for a missing parent, an install file inside the repo, and a forged worktree marker.
5. **The resolver / Lock readers.** I agree with Sonnet that the bridge needs current rules per call, but the two lookups in this plan are not one resolution. A cached install-only fallback in pi or omp can miss newer human gates; `agent/tools.ts:305–307` currently allows a command to pass when nothing matches. Have the bridge send every bash call through the daemon decision, and refuse it when the daemon cannot provide a verdict. Keep the install rules in force when only project resolution fails. Bind the ruling to the authenticated caller, not the optional agent ID passed by `commands/lock.ts:62`; otherwise an unresolved agent can fall into the human path. Specify async hook and timeout behavior for Claude as well as pi and omp, and test daemon unavailability and an install gate change during a long-lived session.
6. **The resolver / `orch settings` inside a repository.** Make the RPC response implementable. Return separate install and effective rows from one daemon snapshot, with per-key source and a typed representation for an additive lock row. The proposed `SettingSource` union cannot express `project + install`, and retaining client-side `rawSetting` can give rows provenance from a different disk snapshot. Name `settings/read.ts:369–383` as the existing precedence helper and update its consumers and fixtures when renaming `settings.json`. Define how both editor views route a save or clear, how `--install --clear` combines, and which view non-interactive output represents. Keep settings writes behind the daemon and explicitly refresh config after a successful install write rather than extending reliance on `fs.watch` under Rule 18.
7. **Every reader / Linked hosts / Tests.** I agree with Opus on the daemon-only resolver, not the shared I/O resolver proposed in Sonnet's first review. Finish the wire plan: remove client-supplied project rules from the worker context, preserve the raw-dispatch distinction, and name the receiving `peerDrive` and linked headless-spawn handlers that compose the header after placement. Cover both paths with two-host fixtures whose checkout and install values disagree. Also correct `repoRootFor` in `policy/space.ts:44–49`: it returns a directory fallback for non-repositories, not a nullable project root alone. Reuse local placement and cwd lookup without inheriting that fallback. Include the test call sites in the `projectRoot()` rename, not just the seven runtime calls; backend fixtures import it, and Bryan runs the real-plexer tests.
