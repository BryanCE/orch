## Improvements

1. **The project file / RPCs.** Containment is not enough to keep project writes away from install gates. If `$ORCH_DIR` is inside the repository and `project.file` names its settings file, the target is inside the root and still holds install gates. Require the project path to differ from the install path, including canonical aliases, before either read or write. Define how the writer handles a missing `.orch` directory, rejects symlink or junction components, and keeps the temporary creation and rename in the verified directory even if a component changes. `repositoryRootOf` also follows `.git` and `commondir` pointers; require a real linked-worktree association before letting that result direct a write to another checkout. Test the in-repo install collision and a forged worktree marker, not just a symlink out of the root.
2. **RPCs / `orch settings` inside a repository.** I agree with Opus that the wire and the caller rules must agree. Show the required `CallerCredential` on all three requests, including the otherwise empty `project-locks`, and name how both bridges supply it. Require orchd to resolve the caller itself; missing or unresolved credentials must not turn a write into an operator write. Independently reject non-project keys in `project-setting-write`, even if the agent holds an install grant for the key. Route set and clear through the same destination selector, including the operator outside a repository. Apply the same operator-only rule for an install write of a project key in the Install editor as for `--install`; otherwise switching tabs reopens the machine-wide write. Say whether setup and the install editor remain available if the project RPC fails.
3. **Which directory a request resolves against / Council readers.** The generic `project-settings` read ignores agent-supplied `cwd`, but the lineup uses that same RPC for `--dir` and the round limit uses the council request directory. An agent in repo A can thus get A's lineup when convening a council in B. Resolve the lineup in orchd using the authorized council directory, or give council resolution its own explicit request and policy. Use the same directory for lineup validation, convene, round, and scores. Do not relax the caller-directory rule for ordinary settings edits. Test an agent convening with `--dir` in a different repository and a lineup that becomes invalid after an install model-policy change. I agree with Sonnet that `council.rounds` can remain a project value under the user's narrowed criterion.
4. **Every reader / Linked hosts / Tests.** Choose one composition point for both local and linked first prompts, after `spawnHeadless` has chosen to launch on this host and before it passes the prompt to either launch branch. `lifecycle.ts:113` declares `spawnHeldLaunch`; the caller is `:100`, and the detached branch at `:102–103` consumes `opts.prompt` instead. The current plan names only delivery to `firstPrompt`, which can leave detached launches with raw text. Update `spawnOnHost`'s explicit forwarding object, and test the final prompt at the receiving side, not only the wire payload. Likewise test that peer dispatch uses the target's rules and a read-only header still omits verification commands.
5. **A project file that is wrong / The resolver.** Pin down absent, invalid, and unreadable files, including a path the resolver refuses to follow. Specify separately what happens on a bare spawn with no prompt, a raw dispatch, a queued task, and a council round whose member is in a repository with an invalid file. The raw-path promise presently conflicts with refusing every dispatch. I would validate before sending any generated header, leave raw delivery alone, and use the queue's normal refusal path rather than silently leaving an attempt stuck. On all lock paths, an invalid or unreadable project file contributes an empty project list, never changes which install gates are read, and never suppresses wrapping for an install match. Add the same malformed-project assertion to both hook families and the daemon ruling.
6. **The merge / RPCs / Sources.** I agree with Sonnet that JSON needs a defined provenance rule even if the combined label is display-only. State what `row.source` is when both lists contribute and when the project's explicit empty list adds nothing. Define stable union order and deduplication. Use registry leaf presence on the exact install snapshot that produced `install`, not a second read that can disagree with the normalized value. `rawValue` is at `settings/shell/state.ts:11`; `:19` is `sourceFor`. Move a pure leaf reader to shared settings rather than importing the shell into orchd. Test a union row in both JSON and the editor. The project editor should display the effective lock list but edit only the project portion, so saving it does not freeze current install patterns into the project file.
