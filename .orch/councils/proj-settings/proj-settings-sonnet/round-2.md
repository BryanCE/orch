## Improvements

1. **Trust, "What approves": close the laundering hole.** A write through orchd "records the new file's hash in the same step". The hash covers the whole file, not the key written. A clone arrives with `workers.verify_commands: ["curl … | sh"]` and no approval. The orch skill's first-wave write then sets `locked_commands.commands`, orchd hashes the file, and the cloned `verify_commands` is approved with it. A human's `orch settings <key> <value>` does the same. Add a rule to Trust: a write against a file that exists and whose hash does not match an approval is refused with the "unapproved project file" message, for the human and for an agent. The human runs `orch settings approve` first. A write against a missing file creates it. A write against an approved file re-stamps it. Also say the resolver hashes the bytes it parses, from one read, so an edit between the hash and the parse cannot be approved by accident. Add a test: unapproved file plus a granted write is refused, and the file stays inert. This is the one change that decides whether criterion 4 is met.

2. **"Which directory each reader resolves against" and "`orch settings` inside a repository": state the no-repository case, because the code already differs from the plan's wording.** `repoRootFor` (`policy/space.ts:44-49`) calls `repoRootOf`, which returns `resolve(cwd)` for a directory outside any repository (`space.ts:36-39`). The plan says to export it and use its answer as the project root, and it also says a directory outside a repository has no project file. Those disagree: the resolver would look for `<dir>/.orch/settings.json` in a plain directory. The plan should say the resolver takes `repositoryRootOf(directory)` and treats `null` as no project file. It should reuse only the placement steps of `repoRootFor` (`hereAgentIfAny`, then `agentLocation().cwd`). Then decide the agent write outside a repository. Today the plan lets it fall through to the install file, which is the original bug: an agent in a scratch directory sets `workers.verify_commands` for the whole machine. Say that an agent's write of a project key with no project root is refused, and that only the operator writes the install file, with `--install`.

3. **"The pattern list an agent's process wraps with": decide the hook's cost and failure.** The claude hook's `gateToolCall` and `preToolUse` are synchronous (`extensions/claude/index.ts:86-88`, `extensions/claude/tool-gate.ts:38`). The plan adds an RPC to every Bash call in both bridges, and each RPC reads and hashes the project file with no cache. Say these three things. First, the RPC has a timeout that is a setting, with a schema entry, a default and a help line (Rule 17); reusing `daemon.report_timeout_ms` is acceptable if the plan says so. Second, `preToolUse` becomes async and its tests change. Third, when orchd does not answer, the install patterns apply, and the plan says the project's extra locks are then skipped. Locks only wait, so skipping them is not a loosening of a gate, but say it, because "never fail open" in the Trust section reads wider than it is. Also say the answer to a project-settings read for a bridge is limited to the pattern lists and not the whole merged settings.

4. **"RPCs" and "`orch settings` inside a repository": say what `SettingSource` carries for a union row.** The type becomes `"flag" | "project" | "install" | "default"`, and a `locked_commands.commands` row shows `project + install`. That string is not one of the four values. Say whether the row carries a list of sources, such as `readonly SettingSource[]`, or a fifth value. `--json` must have one shape. Name the field of the `project-settings` answer that holds it. `rawSetting` (`commands/settings.ts:45`) is kept for install provenance, so say how the editor's Install view and the Project view both use `sourceFor` (`settings/shell/state.ts:36`).

5. **"Words": the rename of `projectRoot()` is bigger than "7 call sites".** There are six calls, in `extensions/claude/index.ts:74`, `extensions/codex/index.ts:44`, `agent/peers.ts:29,35`, `agent/presence.ts:91` and `policy/spawner.ts:54`. The rename also reaches the `projectRoot` field of the `peer-view` request (`daemon/client/protocol.ts`, read in `handlers/table.ts`) and the tests and helpers that use it (`backend-herdr.test.ts`, `backend-tmux.test.ts`, `herdr-notify-hardening.test.ts`, `peer-identity.test.ts`, `helpers/daemon-client.ts`). `ORCH_PROJECT` and the presence `project` field keep the old word. Either list all of that and say the env var and the presence field are renamed too, or say they stay and the plan's claim that "project means one thing" is limited to the TypeScript identifier. Rule 8 says to fix every writer, reader and fixture in one change, so list them.

6. **"The resolver" and the write path: say how a write is serialised and ordered.** The install file's writer takes a file lock (`lock.retries`, `lock.interval_ms`, `lock.stale_ms`). The project write is read, modify, hash, temp file, rename, record, inside orchd. Two granted agents writing two keys at the same moment would each read the old file and the second rename would drop the first key. Say orchd serialises project writes per root, and that the hash row and the rename succeed together or the row is not written. Say what happens when the rename succeeds and the store write fails: the file is then unapproved, and the writer reports that.

7. **"Linked hosts": say what travels and what the local orchd must not do.** The `peer-drive` `dispatch` action gains the worker context (`protocol.ts:470`). Say which fields it carries (`maySpawn`, `spawnerRepliable`, place) and that it carries no `verifyCommands` and no gated list, so a caller's rules cannot govern a target. Say that the local orchd's `dispatch` (`handlers/write.ts:327-332`) composes no rules itself when the target is on a linked host, so the two hosts do not both add rules. Say what an old-version peer does with the new field; under Rule 8 the answer is that it is refused, so say so. Add a test for the linked dispatch and for the first prompt of a linked spawn.

8. **"Tests": add the cases the new rules need.** The list has none for: the write against an unapproved file (item 1), an agent's write with no project root and `--install` from an agent (item 2), the hook's fallback when orchd does not answer (item 3), a union source row (item 4), the `project-settings-approve` verb refused for a non-operator, a rename that fails after the hash row is written, and the linked-host header. Also list the protocol tests for the three new RPCs and the store test for `project_settings_approvals`. `project-settings.test.ts` should say which of its cases need a `.git` directory and which need a real symlink; a symlink test is a filesystem test that runs under `test/` and creates files only under the temp dir.

9. **"`orch settings` inside a repository": list the documents that change.** The new verb `orch settings approve` and the flags `--install` and `--clear` need entries in `src/commands/registry.ts`, `help/settings.md` and `skills/orch/reference/commands.md`. `help/settings.md:10-11` says what an agent may write, and `README.md:233-263` describes where `workers.verify_commands` and `locked_commands` live; both now say the value lands in the project file. "The skill needs no edit" is true for behaviour, but `skills/orch/reference/fleet.md:9-15` still tells the orch to run `orch settings workers.verify_commands …` and should say the value is the project's. Rule 8 puts every writer, reader and doc in the same change.

10. **"The project file / Where" and Trust: bind the approval to the path.** `project.file` is an install setting. If the human changes it, the approval row (root, sha256) can match a different file with the same bytes, or an old row can match a file that has moved. Add the relative path to the row, or say that changing `project.file` voids every approval. Also give `project.file` a validator: relative, no `..`, no absolute path. The real-path check in "Path safety" catches an escape at read time, and the setting should refuse it at write time too.
