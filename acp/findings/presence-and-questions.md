## States

The complete `AgentState` vocabulary is `idle`, `working`, `waiting`, `blocked`, `asking`, `done`, `error`, `aborted`, `exited`, `unknown`; `AgentState` is derived from `AGENT_STATES`, `packages/orch/src/agent-state.ts:10-12`. The schema accepts only those values, and run-end states are `done`, `error`, `aborted`, `exited`, `packages/orch/src/agent-state.ts:15-24`.

- Status RPC patches are parsed against this state vocabulary; status is patch-merged, absent fields preserved and null clears nullable fields, `packages/orch/src/daemon/client/protocol.ts:608`, `packages/orch/src/store/status-rows.ts:22-35`.
- There is no global allowed-from/allowed-to transition graph: `acceptStatusReport` accepts a valid state and publishes only when it differs from the previous valid state, `packages/orch/src/daemon/server/status-report.ts:88-103`.
- While a row is `waiting` for a command lock, a harness's `working` report is retained as `waiting`; `packages/orch/src/daemon/server/status-report.ts:75-77`.
- The pi/omp agent layer writes `blocked` when a blocked signal is active; its status writer and patch are at `packages/orch/src/agent/presence.ts:115-151`. Its settle handler records `done` (or `idle` for empty text), while error/abort reports retain those terminal states, `packages/orch/src/agent/tools.ts:324-340,354-389`.
- Claude's hook integration reports `idle` on session start, `working` on prompt submission, `asking` on permission/question, `done` on stop and `error` on stop failure, `packages/orch/src/adapters/claude.ts:201-204` and `packages/orch/extensions/claude/index.ts:108-150`.
- A dead process with a valid non-`exited` status is marked `exited` by the liveness tick; `packages/orch/src/daemon/server/status-report.ts:166-187`. Explicit close ends the agent row and publishes `closed`, `packages/orch/src/daemon/server/handlers/lifecycle.ts:160-188`.

## Turn end and result

- Pi/omp settle on their harness-specific settle event (`agent_settled` for pi, `session_stop` for omp), `packages/orch/extensions/pi/index.ts:15` and `packages/orch/extensions/omp/index.ts:22`; `settleAgentRun` writes terminal status, and writes a result when the accumulated assistant text is nonempty, `packages/orch/src/agent/tools.ts:354-389`. For an `agent_end` whose last assistant message has stop reason `error` or `aborted`, the agent layer sets that state and reports partial text plus an error marker, `packages/orch/src/agent/tools.ts:307-352`.
- The pi/omp result is assembled from assistant messages and usage; context reconciliation scans the harness session branch and, if the harness is idle while orch still says `working`, changes to `done` (latest text) or `idle` (no text), `packages/orch/src/agent/presence.ts:199-257`.
- Claude hooks report successful stop as `done` plus transcript-derived text and issue `report-result`; stop failure reports `error`; permission/question notifications report `asking`, `packages/orch/extensions/claude/index.ts:119-150`. Claude adapter state fallback uses signal/nonzero exit => `error`, zero exit => `done`, otherwise `unknown`, `packages/orch/src/adapters/claude.ts:262-273`.
- Codex's notify extension derives state from its event stream/exit code and sends result on completion, `packages/orch/extensions/codex/events.ts:25-29,158-171` and `packages/orch/extensions/codex/index.ts:31-56`.
- `report-status` creates/updates run observations from status; `report-result` settles the run with state `done` and result text, `packages/orch/src/daemon/server/status-report.ts:49-75,127-162`. `runs` columns are `dispatch_id`, `agent_key`, `adapter`, `model`, `space`, `task`, `state`, `started_at`, `finished_at`, `tokens_in`, `tokens_out`, `cache_read`, `cache_write`, `cost`, `turns`, `result`, `last_error`, `packages/orch/src/db/schema.ts:71-90`. `upsertRun` inserts or updates by dispatch id and preserves initial `startedAt`, `packages/orch/src/store/run-rows.ts:56-71`; status reports and result reports call it. The status row establishes a run when dispatch id is present and state is not idle; result report or terminal status can update/settle it, `packages/orch/src/daemon/server/status-report.ts:49-75,127-162`.
- Result text sources include the daemon's result report and, for Claude, transcript JSONL then native command output then presence last text, `packages/orch/src/adapters/claude.ts:279-295`; Claude hook stop extracts transcript text at `packages/orch/extensions/claude/index.ts:119-127`. Codex extracts its result from native event output, `packages/orch/src/adapters/codex.ts:156`. Pi/omp use presence result then the session entry fallback, `packages/orch/src/adapters/pi.ts:375-385` and `packages/orch/src/adapters/omp.ts:140-150`. The inspected result paths do not infer a result from a plexer screen.

## Questions end to end

1. Agent tool `orch_ask` creates a question id and timestamp, truncates the question, then posts an `AgentNotice`; `packages/orch/src/agent/tools.ts:104-129`. Notice wire shape is at `packages/orch/src/shared/bridge-message.ts:30-37`; the daemon client sends it over the bridge link when possible or as a `question` RPC otherwise, `packages/orch/src/agent/daemon-client.ts:254-258`.
2. The `question` RPC calls `recordAgentQuestion`; it verifies the agent row exists and calls `recordQuestion`, `packages/orch/src/daemon/server/handlers/table.ts:211` and `packages/orch/src/daemon/server/handlers/lifecycle.ts:273-277`. `recordQuestion(directory, {id, agentId, question, askedAt})` settles an existing open question for that agent before inserting a new row, `packages/orch/src/store/question-rows.ts:8-27`.
3. `questions` columns: `id` primary key, `agent_id`, `question`, `asked_at`, nullable `answered_at`, nullable `answer`; `answered_at IS NULL` means open and settled null-answer means superseded, `packages/orch/src/db/schema.ts:46-57`. `pendingQuestion(directory, agentId)` filters to unanswered rows and returns at most one (`limit(1)`), `packages/orch/src/store/question-rows.ts:41-47`; `pendingQuestions` lists all open questions, `packages/orch/src/store/question-rows.ts:49-54`. Thus one agent has at most one open question; `recordQuestion` enforces this by settling prior open rows in its transaction, `packages/orch/src/store/question-rows.ts:14-25`.
4. `orch questions` maps pending rows to views, including host/name/space, `packages/orch/src/daemon/server/handlers/table.ts:211-212`, `packages/orch/src/daemon/server/handlers/lifecycle.ts:289-301,323-329`. The listing includes linked agents by querying each relevant host's `peer-questions`, `packages/orch/src/daemon/server/handlers/lifecycle.ts:303-317`.
5. `orch answer` reaches `answerHere` on the agent's host; it requires a matching pending question, delivers an `answer` control message and waits for acknowledgement, then calls `settleQuestion`, `packages/orch/src/daemon/server/handlers/write.ts:347-367,370-380`. The answer delivery has `{action:"answer", text, questionId}` shape, `packages/orch/src/shared/bridge-message.ts:12`; the agent answer waiter accepts the matching question id, `packages/orch/src/agent/presence.ts:286-320`.
6. `settleQuestion` updates only a matching still-open id, setting `answered_at` and `answer`; late/duplicate answers return false, `packages/orch/src/store/question-rows.ts:29-39`. A newer question supersedes its predecessor with `answer: null`, `packages/orch/src/store/question-rows.ts:14-25`.
