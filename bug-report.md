# orch bug report — completed fleets never wake the Claude Code orchestrator

**Date:** 2026-08-25
**Session:** t3reports, TL-commission-selection fleet (`bounds`, `goldens-02`)
**Severity:** workflow-breaking. Both workers finished; the orchestrator sat idle until Bryan noticed and intervened. This is the second failure mode of the same class (the first being poll loops).

## What happened

1. Orchestrator dispatched two workers, then armed the documented watch as a
   Claude Code background Bash task:
   ```bash
   orch events --mine --status done,error,blocked,asking --json | jq -r --unbuffered '...'
   ```
2. Both workers hit `done`. The stream **did** print `pi: done` lines into the
   background task's output file — the daemon side worked perfectly.
3. Claude Code only re-invokes the model when a background command **exits**.
   `orch events` is an infinite stream by design, so it never exits, so the
   wake never fires. The output file filled up with exactly the lines nobody
   was awake to read.

## Root cause

Mismatch of contracts:

- **orch's contract:** "subscribe and I will push lines forever."
- **Claude Code's contract:** "I wake the model when a tracked task *completes*
  (background Bash exit, Monitor condition met, subagent finish)."

A never-exiting stream satisfies neither a human tail nor the harness. The
current orch-cli skill tells the model to arm the stream, which produces a
watch that *looks* armed and is functionally a no-op. And any fix that lives
only in skill prose ("remember to also arm a Monitor") depends on the model
remembering — the exact dependency we need to delete.

## What orch should ship (ranked)

### 1. `orch await` — a watcher that EXITS (core primitive, smallest change)

```bash
orch await --mine [--dispatch <id>...] [--timeout <sec>]
# blocks; exits 0 the moment every watched dispatch reaches a terminal/attention
# state (done|error|blocked|asking); prints one JSON line per agent:
# {"name":"bounds","state":"done","dispatchId":"...","result":"<first 200 chars>"}
# exits 2 on timeout, 3 if a watched pane vanished
```

Why this shape: `run_in_background` Bash + a command that terminates IS the
harness's native notification channel. No hook, no MCP, no polling. The skill
line becomes "after dispatching, run `orch await --mine` in background" — and
even that memory dependency disappears with #2.

`--attention` variant: exit as soon as ANY agent needs attention
(`asking|blocked|error`) rather than waiting for all — the orchestrator wants
to be woken for a question immediately, not after the siblings finish.

### 2. `orch dispatch --spawn-awaiter` + `orch claude install-hooks` (removes the memory dependency)

Two complementary pieces:

- **`orch claude install-hooks`** writes Claude Code hook entries into the
  project's `.claude/settings.json` (idempotent, versioned):
  - **PostToolUse hook** matching Bash commands that contain `orch dispatch`
    or `orch work`: emits hook output telling the model
    `"orch: N dispatches in flight and no awaiter running — start: orch await --mine (background)"`
    when `orch await` is not already alive (`pgrep -f 'orch await'`). The
    reminder is generated by the OS, not remembered by the model.
  - **Stop hook**: runs `orch status --json`; if any pane spawned by this
    session (`spawnedBy` match) is still `working` or has an uncollected
    `done` result, **block the stop** with reason
    `"orch fleet not collected: bounds=done (uncollected), goldens-02=working"`.
    This is the backstop that makes "orchestrator ends turn while workers run"
    structurally impossible instead of merely discouraged.
- **`--spawn-awaiter`** (or `settings.json: autoAwait=true`): dispatch itself
  guarantees an awaiter process exists for the session, so even the PostToolUse
  reminder is belt-and-suspenders.

The Stop hook is the key piece for "not dependent on the harness remembering":
hooks are executed by the harness deterministically on every stop, with zero
model cooperation required.

### 3. Result push into the transcript, not just a state flip

`done` today is a state; the result still needs an `orch result` call the model
must remember. `orch await` (#1) should inline the result text (or a
`--full-results` flag) so the wake-up event carries the payload and collection
cannot be forgotten.

### 4. Longer term: expose orchd as an MCP server (`orch mcp serve`)

If dispatch were an MCP tool call, the harness would track it as ITS OWN task
— completion notification becomes native (`<task-notification>`), permissioned,
and visible in /tasks, with no Bash plumbing at all. Tools: `orch_spawn`,
`orch_dispatch` (returns when terminal — the await is built in), `orch_steer`,
`orch_status`. Streaming panes stay in the TUI; the MCP layer only carries
lifecycle + results. This is the "correct" integration; #1+#2 are the pragmatic
ones shippable now.

## Non-solutions (tried or considered)

- `orch events | jq` in background Bash — never exits, never wakes (this bug).
- Poll loops (`while true; orch status`) — banned in the skill, correctly.
- "Remember to arm a Monitor" in skill prose — fails on compaction/turn ends;
  the model's memory is the single point of failure the design must remove.

## Interim workaround (until `orch await` exists)

Wrap the stream so it EXITS on first relevant event — this is what the
harness can actually be woken by:

```bash
orch events --mine --status done,error,blocked,asking --json | head -n 1
```

run via Bash `run_in_background`, re-armed after each wake while dispatches
remain in flight. Or the Claude Code `Monitor` tool with an until-condition on
`orch status --json`. Both still depend on the model remembering — hence this
report.
